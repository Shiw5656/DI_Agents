# Data Vault Model Review Issue Register

| Issue ID | Issue Title | Category | Severity | Affected Object | Explanation | Recommendation |
|---|---|---|---|---|---|---|
| DV-001 | Missing Effective Historization Metadata in Satellites | Data Historization | High | Various Satellite Tables (e.g. [Ib].[SatStudentPersonal], [Ib].[SatSchoolDetails]) | Satellites such as [Ib].[SatStudentPersonal] and [Ib].[SatSchoolDetails] lack strict enforcement of non-overlapping effective dates (`LoadDts` and `LoadEndDts`). This can allow duplicate or overlapping records for the same business key and timeframe without detection. | Add CHECK constraints to prevent overlapping effectiveness periods. Ensure overlapping records are controlled during ETL logic. |
| DV-002 | Ambiguity in Multi-Component Business Keys | Relationship Grain | High | [Ib].[HubCourseSection].[CourseSectionBk] | The concatenated business key ([CourseSectionBk]) contains multiple components separated by `||` without a documented standard on parsing rules. This can lead to ambiguities during canonical modeling. | Document the parsing and composition rules for `CourseSectionBk`. Specify how individual components (e.g., `SchoolCode`, `TermCode`, etc.) are constructed and validated downstream. |
| DV-003 | Lack of Referential Integrity on Coded Attributes | Referential Integrity | Medium | [Ib].[SatAttendanceDetails].[AttendanceStatusCode] | `AttendanceStatusCode` in the satellite refers to coded values but has no foreign key to enforce referential integrity with [Ib].[RefAttendanceStatus]. This can result in uncontrolled value drift. | Add a foreign key constraint linking `AttendanceStatusCode` to [Ib].[RefAttendanceStatus].[AttendanceStatusCode]. |
| DV-004 | Missing Hash Key Constraints in Reference Table | Structural Design | Medium | [Ib].[RefAttendanceStatus] | Reference tables like [Ib].[RefAttendanceStatus] do not include hash keys or historization metadata, which limits their alignment with Vault principles. | Add hash keys and modular historization (LoadDts/LoadEndDts) to track changes to reference data over time. |
| DV-005 | Cryptic Naming of Link Relationships | Canonical Modeling Risk | Medium | Various Link Tables (e.g., [Ib].[LnkSectionOffering], [Ib].[LnkSectionTeacher]) | Link names like `SectionOfferingHk`, `SectionTeacherHk`, etc., do not clearly describe the relationship or grain, increasing ambiguity for canonical modeling and downstream mapping. | Rename link primary keys or provide detailed metadata describing relationship grain (e.g., `SectionOfferingRelationshipHk`). |
| DV-006 | Nullable Columns in Satellites | Structural Design | Medium | Various Satellite Tables (e.g., [Ib].[SatStudentPersonal.FirstName]) | Many attributes in satellites, such as `FirstName` in [Ib].[SatStudentPersonal], are nullable without default values. This risks inconsistent interpretation during historization or lookups. | Review nullable attributes and apply default values (e.g., 'Unknown'). Alternatively, explicitly document the cases where null values signal `missing` vs. `non-available` data. |
| DV-007 | Business Vault Entity Without HashDiff | Structural Design | Medium | [Ib].[BvSatAttendanceSummary] | The computed satellite [Ib].[BvSatAttendanceSummary] lacks a `HashDiff` even though it tracks aggregated attendance data at the grain of [EnrollmentHk]. This affects Delta Detection in downstream ETL. | Add a `HashDiff` column to support change tracking for derived aggregates. Use SHA2_256 hashes of select columns to enable computed Delta Detection. |
| DV-008 | Grain Limitations in Attendance Links | Relationship Grain | High | [Ib].[LnkAttendance] | The link [Ib].[LnkAttendance] does not enforce uniqueness for `AttendanceDate`, `PeriodNumber`, and `StudentHk`, allowing duplicates for the same student-day-period attendance record. This risks logical integrity. | Add a unique constraint on the combination of `StudentHk`, `AttendanceDate`, and `PeriodNumber` to enforce correct grain. |
| DV-009 | Primary Key Index Selection | Structural Design | Medium | Various Tables (e.g., [Ib].[HubStudent], [Ib].[SatStudentPersonal]) | Primary keys like [PK_HubStudent] are non-clustered while unique clustered indexes are applied on business keys (e.g., [UX_HubStudent_Bk]). This indexing strategy may not optimize query performance for hash key lookups. | Review and adjust indexing strategy to optimize query performance. Consider clustering on hash keys where frequent joins are expected. |
| DV-010 | Absence of Data Quality Profiling for Testing Gaps | Input Limitation | Critical | All Tables | No profiling results were supplied with the DDL input. This review cannot confirm whether duplicate records, overlapping histories, or value drift occur in practice. | Conduct data profiling to identify duplicate hubs, overlapping satellite records, or uncontrolled link relationships. Rerun the review with profiling evidence. |

Each issue's explanation and recommendation have been supported by the DDL structure provided. Issues related to metadata gaps and referential integrity risks are critical for ensuring the model’s robustness across canonical modeling and Microsoft Fabric implementation. Data profiling results are needed to confirm actual data defects.
